# Restaurant

AI 餐厅建站与订桌平台。

商家上传菜单、图片和餐厅资料，由 Agent 引导补齐信息，生成可预览、可发布的餐厅 HTML 网站。商家统一登录平台管理预订和查看访问数据。

## 当前状态

已确认并开始实现：React＋Vite＋TypeScript 前端，Fastify＋TypeScript 后端，PostgreSQL 16，邮箱密码与安全 Cookie 会话。

当前已落地商家账户、餐厅草稿、素材上传管理及 DeepSeek V4.1 Flash 网页引导/生成、隔离预览与本地版本发布回滚，使用真实 PostgreSQL 与私有文件存储；不是模拟登录或假模型生成。菜单JPG/PNG可直接发送给同一多模态大模型识别（不接独立OCR），获得可编辑、可人工确认的菜单草稿；确认内容可进入下一次网页生成。正式平台二级域名/云端发布、自定义域名、顾客预订与数据看板尚未完成。

素材功能入口：登录 → 选择餐厅 → **菜单与图片**。支持PDF/JPG/PNG上传、列表、授权查看/下载和二次确认删除。见[功能与手动测试说明](outputs/菜单与图片上传-功能与测试说明.html)及[素材OpenAPI](backend/contracts/assets.openapi.json)。

**尚未对真实商家开放生产服务：** SMTP、正式域名与部署、正式条款/隐私内容和告警均未完成。邮箱验证/改密任务真实落入outbox，但缺少发送服务时不会假称邮件已送达；自动化测试通过仅表示当前本地闭环已验证。

前后端源码、依赖清单和构建入口分开；后端没有为每家商家生成独立业务服务器。生成网页保留不可变HTML/素材快照；本地只读站点使用独立4174端口，与管理平台隔离。正式公网域名与托管部署仍未完成。

已明确的项目原则：

- 前后端分离，从首版采用真实数据库、完整商家注册认证与生产级配置。
- 平台本身与生成并上线的餐厅服务均需满足生产级要求。
- 首版字段与业务契约固定，商家不修改数据库结构。
- “订餐”指订桌订位，不是菜品订单或外卖。
- 商家在平台统一管理，不为每家餐厅生成独立后台。
- 首版不做自动容量和桌位分配；预订的人工确认流程仍是待确认建议。

## 网页生成与本地发布

登录 → 选择餐厅 → **网页生成**。输入自然语言与Agent对话，核对已有资料，最多选择8份已上传素材，确认公开使用后生成。模型采用官方 `deepseek-flash`（DeepSeek V4.1 Flash），密钥仅后端使用，不进入浏览器或仓库。

- 菜单原文件可查看/下载；菜单识图页可直接用视觉大模型读取JPG/PNG，人工确认的菜名、描述与原文价格才进入新网页。PDF视觉识别本轮不支持。
- 网页生成改用原生工具ReAct：读取能力/资料 → 自主Plan/TODO → 写HTML/CSS → 真实语法检查 → 错误反馈修复 → 检查通过完成。正常静态标签和现代CSS函数不再因过窄白名单失败。
- 固定餐厅事实与确认菜单由后端填充；运行隔离继续禁止模型脚本、任意外部资源和商家特权API。校验反馈具体文件/行/列/原因，组件展开后的最终HTML也检查结构。
- 用户要求先跑通并测量用量：当前观察模式取消累计token、模型调用/动作/稿次/修复轮次及总运行时长门禁；只按实际用量记录，不再用UTF-8输入预留误杀。单次模型请求保留75秒网络超时与16k输出窗口、静态文档大小和权限边界。费用持续累计，可手动停止；缺用量、超时、余额不足或撤权停止，不盲重试网络请求、不返回假模板。
- 007迁移保存每次模型调用的真实输入/输出/总tokens、耗时、已知/未知账单，取消后仍允许原调用迟到补账但不复活任务。短期租约由有效计费前授权检查续期，进程失联后按租约失败，不把租约变成总运行时长限制。
- 电脑/手机预览使用无同源权限的受限iframe；预览文档自包含，网页内菜单/联系方式锚点可点击跳转，切换尺寸从顶部重绘，大图缩略或降级为占位，可另开新窗口查看原图。选择版本并确认可发布到 `http://localhost:4174/s/<slug>`，可选择历史版本回滚。
- 当前网址仅本机可用，不是已上线的公网二级域名；订位后端已实现申请、商家处理、顾客管理链接与取消，公开站点表单、商家预订界面和真实邮件发送仍未完成；订阅表单未开放。真实云端托管/HTTPS/DNS仍须配置与验收。

最新用量与限制调整：[真实run token实测](outputs/网页生成-用量观察与实测报告.html)；预览锚点与尺寸切换修复：[网页预览修复说明](outputs/网页预览-锚点与尺寸切换修复说明.html)。用户实际餐厅的独立实测HTML只保留在被Git忽略的 `outputs/local-tests/`，未自动发布；代码及脱敏用量报告可以提交。

历史说明：[ReAct循环与接口能力](outputs/网页ReAct循环与接口能力-交付说明.html)、[给模型的真实能力契约](backend/contracts/website-agent-capabilities.json)、[原生工具真实模型样例](outputs/网页ReAct-真实模型样例.html)及[执行轨迹样例](outputs/网页ReAct-执行轨迹样例.json)。样例为明确虚构的工程验证，不代表真实餐厅，也未自动发布。

模型能力说明区分：已实现的商家账户/餐厅/素材/菜单/生成发布接口，只有平台能鉴权调用；模型拿到只读快照和虚拟草稿工具。顾客订位后端已经实现，但顾客账号、订阅和统计接口仍未实现，不能宣称已经接通，不把后台Cookie或私有API写进公开网页。

## 订位后端

订位按“申请待商家确认”实现：**提交不等于有位**，不做自动容量、桌位或拼桌分配。008迁移新增 `reservations`、`reservation_events`、`reservation_access_tokens`，并扩展邮件队列、审计枚举与餐厅订位字段权限。

- 商家：`GET/PATCH /api/v1/restaurants/:id/reservations/settings` 开启或停订、设置隐私说明版本；`GET /api/v1/restaurants/:id/reservations` 列表与详情；`POST .../:reservationId/decision` 确认或拒绝；`POST .../:reservationId/cancel` 取消。均需登录、CSRF与revision校验。
- 顾客：`POST /api/v1/public/restaurants/:slug/reservations` 提交申请，返回一次性的高熵管理令牌；凭令牌 `GET /api/v1/public/reservations/:token` 查看，`POST .../cancel` 取消。游客无需注册，不能凭邮箱或编号查询。
- 校验餐厅时区与营业段（含跨午夜）、`accepts_requests`、90天窗口、夏令时不存在或重复时间；人数1–20；不声称实时有位。
- 状态机 `pending → confirmed / declined / cancelled`，`confirmed → cancelled`；终态不可改；每次变更递增revision并写不可变事件。
- 通知邮件只在同一事务排队；SMTP未配置时不发送、不伪造成功。状态通知复用原管理链接，不轮换令牌，避免顾客失去查看入口。
- 生成网页新增固定 `<restaurant-reservation>` 组件：模型提示词与能力契约要求开启订位时必须显式写入且仅写一次；服务端在漏写时兜底补全。未开启订位时服务端不渲染该块，即使模型误写也不会出现“暂未开放”占位。生成页只放平台入口，不运行表单或脚本。
- 订位入口指向平台固定页面 `/s/<slug>/reserve`，使用同源表单提交；成功页给出 `/r/<token>` 管理链接，可查看状态和取消。只有该页面允许 `form-action 'self'`，生成网页仍保持沙箱与禁表单。
- 网页生成页新增“在线订位设置”：开关、给顾客的说明、隐私说明版本；保存会递增餐厅revision，需要重新核对网页生成确认。营业时间中至少要有一段勾选“此段允许申请”。
- 商家预订管理页面尚未实现；当前需用商家API处理。真实邮件发送、访问统计和公网部署仍未完成。

详见[订位后端交付说明](outputs/订位后端-数据库与接口交付说明.html)。

## 菜单图片直接交给大模型

登录 → 选择餐厅 → **菜单与图片**，将JPG/PNG按“菜单原文件”用途上传；点击“菜单图片交给大模型”或进入 **菜单识图**。

1. 选择1–4张本店菜单图片（每张≤10MiB、总计≤20MiB），明确同意发送给DeepSeek后识别。
2. 后端从私有存储读取、校验图片，以base64多模态输入送入 `deepseek-flash`；不接独立OCR、不给模型公开文件URL。
3. 结果保存为未确认草稿，包含分类、菜名、描述、价格原文、内部核对备注与不确定提示；模糊价格留空，不计算或猜测币种。
4. 人工修改并保存、核对确认。保存或再次识别会撤销当前确认；失败保留原菜单。
5. 到网页生成核查状态、确认后生成新版。只有确认菜单进入不可变快照，旧网页和已发布版本不会自动变化。

当前最多20分类/80菜品；PDF仍仅上传查看，不送进识图接口。菜单识别、Agent对话与网页生成共享每账号滚动24小时30次任务额度；明确发送图片会产生模型费用。网页模型不会收到内部核对备注或warnings。来源引用用于保留可追踪性，不允许直接删除成功识别任务引用的菜单图片。

见[功能与手动测试说明](outputs/菜单直接识图-功能与测试说明.html)、[合成输入图片](outputs/菜单识图-合成测试图片.png)与[真实模型结果](outputs/菜单识图-真实模型结果.json)。样例是工程测试，不是任意真实菜单准确率保证。

## 本地运行与检查

需要 Node.js 22.12–22.x、PostgreSQL 16 工具及 OpenSSL。独立源码使用相对导入，私有 `.env.local`、证书、数据库和任何密钥都不提交。

新克隆、没有依赖目录时，分别安装：

```sh
npm --prefix backend ci
npm --prefix frontend ci
```

当前机器的 `node_modules` 是通往隔离依赖目录的本地链接，不纳入 Git；不要对现有共享依赖链接执行会删除目录的清理操作。其它机器正常独立安装无需此链接。

专用本机数据库初始化（首次运行生成私有开发配置；不扫描或修改其它数据库集群）：

```sh
node backend/scripts/setup-local.mjs
npm --prefix backend run migrate
```

脚本默认查找 `/opt/homebrew/bin` 的 PostgreSQL 16；其它环境用 `PG_BIN_DIR` 指定真实工具目录。数据库只监听127.0.0.1:55439，开发库与测试库分开，应用与迁移角色分开；不启用trust认证。开发HTTPS证书为本地自签名证书，不安装全局信任、不能用作正式证书。

网页生成密钥放 `backend/.env.deepseek.local`，格式参见 `.env.example` 的DEEPSEEK配置；开发后端自动加载该私有文件。官方接口固定 `https://api.deepseek.com`，model固定 `deepseek-flash`。没有密钥时，读取已有网页版本仍可用，付费生成返回明确错误。

分别在三个终端启动：

```sh
npm --prefix backend run dev
npm --prefix frontend run dev
npm --prefix backend run sites:dev
```

打开 `https://localhost:5173`。后端只监听本机4000，前端代理 `/api`，浏览器使用Secure、HttpOnly、SameSite Cookie。`EMAIL_MODE=disabled`只排队不发信；没有SMTP时不能让普通新用户绕过邮箱验证。

检查与构建：

```sh
npm --prefix backend run contract
npm --prefix backend run typecheck
npm --prefix backend test
npm --prefix backend run build
npm --prefix frontend run build
```

后端测试必须使用专用真实测试库，启动前会核对库名/角色/端口，绝不清空开发库。浏览器测试需要已验证专用账户，通过私有环境提供 `E2E_EMAIL`、`E2E_PASSWORD`。`backend/test/prepare-ui.ts`仅用于指定本地测试环境，通过正常注册/验证接口准备夹具：它在测试代码中读取短期加密令牌，不是线上绕过入口，也不表示真实SMTP已验收。生产构建不包含test目录。

生产运行使用构建结果 `backend/dist/src/index.js`，由受控部署注入配置；必须启用并配置SMTP和HTTPS，不允许运行时回退模拟DB或disabled邮件。数据库迁移另用独立角色运行，应用拒绝超级用户/DDL角色。公开网站、正式证书、反向代理、邮件签名与备份告警等须完成对应部署验收后才可上线。

## 菜单与图片素材功能

- PDF仅作为菜单文件，最大20MiB/100页；JPG/PNG最大10MiB/2000万像素，单帧图片。
- 上传必须选择固定用途并声明有权使用。检测实际字节与MIME/扩展一致，不接受SVG/GIF/HTML、加密或已知主动内容PDF；这是技术检查，不是全面防病毒或版权认证。
- 图片会完整解码、旋转、重编码清除EXIF/GPS等元数据，保存的图片大小/摘要可能不同于本机原文件；PDF保留原始字节并只提供附件下载。
- 所有素材私有、按餐厅隔离；授权通过API读取，不返回storage_key或公开静态URL。
- 每店最多100份有效素材、200MiB；每进程同时最多2个文件传输，超出返回明确限流提示。
- 本地开发用真实私有文件目录；正式环境必须配置S3兼容私有对象存储。S3适配已写，真实账户/ACL/删除语义未验收，不把本地运行当作云端生产完成。
- 新增002素材/引用保护、003上传意图迁移，保持已执行001不变。对象写入前持久化意图；失败/崩溃用到期补偿和条件校验，不盲删不属于该上传的文件。
- 删除仅针对所选平台素材，不删除你本机原文件；引用中的素材禁止删除，墓碑不可复活。物理失败有内部补删状态。
- PDF结构解析移至独立短命进程，设5秒与96MiB JS堆预算；不能把JS堆限制声称为完整RSS隔离，正式运行仍需OS/容器限制与安全运维验收。

精确补偿清理有独立入口，不能用通配或全目录删除代替：

```sh
npm --prefix backend run assets:cleanup
```

部署时须配置受控定期执行与失败告警；本轮未安排云端定时任务。数据库备份不包含对象字节，正式恢复方案必须覆盖数据库与对象存储引用一致性。本轮没有接入AI图片/识别/生成，也没有替用户跑浏览器验收。

## 开发路线

1. **接口与技术方案**：确认当前模块的输入、权限、状态规则和技术选择。
2. **生产底座与账户**：真实数据库、迁移、认证、租户隔离，完成商家注册和餐厅资料闭环。
3. **菜单与素材**：上传、识别、修改、确认；受控素材和版本管理。
4. **预订与通知**：固定顾客组件、商家处理、游客授权和可靠邮件。人工确认规则仍需明确。
5. **Agent 与生成发布**：引导补资料、生成 HTML、预览隔离、批准发布和回滚；生成能力可提前小范围验证。
6. **看板、顾客账号与订阅**：准确指标、可选注册、按餐厅管理的营销同意及退订。
7. **双层上线验收**：分别验证平台与公开餐厅网站的完整流程、安全、故障和恢复。

每阶段都实现必要的后端接口、对应页面和测试，生产要求随模块落实，不以模拟数据版本代替真实业务。此前顾客可选注册和邮件订阅需求保留；人工确认、邮件群发、账号体验和域名等细节在相关模块前确认。
