## 1. 本轮完成范围

第一闭环：商家申请注册 → 邮箱验证 → 登录 → 创建餐厅草稿 → 查询/修改餐厅资料及周营业时间。

提供14条路径、17个业务操作和21个固定schema；包含输入输出、权限、错误、幂等及并发行为。不存在“直接对users/restaurant_members开放通用CRUD”的接口。

## 2. 认证协议建议

建议以同源网关对外暴露 `/api/v1`，前端与后端仍可独立部署。API使用不透明会话Cookie；不把登录凭据保存在localStorage或生成的HTML中。这是协议建议，需在技术方案确定时确认，并非已选择框架/认证供应商。

- 会话Cookie：`__Host-restaurant_session`，Secure、HttpOnly、Path=/、SameSite=Lax，不设置Domain。
- 登录前的短期认证上下文：`__Host-restaurant_authflow`，不授予商家权限。
- 写操作携带绑定该上下文的 `X-CSRF-Token`，服务端同时检查允许的Origin，不能只看header存在。
- `/auth/csrf` 获取与当前session或匿名authflow绑定的token；登录成功轮换会话和CSRF上下文。GET缺少Origin时仅接受网关核验的同源请求，证据不足403，不简单放行；同源Referer和Fetch Metadata需按严格规则验证。
- 401附 `WWW-Authenticate: Session realm="restaurant-platform"`；Session是本平台声明的Cookie会话认证挑战，客户端进入登录流程，不误称HTTP Basic/Bearer认证。
- 邮箱验证/改密的显式POST由高熵动作令牌授权，不借用ambient登录会话；GET页面或邮件扫描器不消费令牌、不改变状态。
- 每次请求验证会话有效期、撤销、账号状态和餐厅归属。仅签名正确并不足以证明仍有权限。
- 生成的餐厅网站的游客及顾客认证协议，在对应模块单独定义，不随此处管理平台Cookie协议自动开放跨域权限。

首版是邮箱＋密码流程。若选择托管认证，由供应商负责成熟密码处理和必要会话能力，平台提供同样的业务契约，不复制托管密码到本数据库。

## 3. 接口列表

路径均相对 `/api/v1`。

| 方法 | 路径 | 功能 | 权限/成功结果 |
| --- | --- | --- | --- |
| GET | /auth/registration-policy | 当前条款、隐私版本、密码规则及支持语言 | 公开，200 |
| GET | /auth/csrf | 当前认证上下文CSRF token | 受Origin限制，200 |
| POST | /auth/register | 申请商家注册 | authflow或session＋CSRF，202 |
| POST | /auth/verification-emails | 重发验证邮件 | authflow或session＋CSRF，202 |
| POST | /auth/verify-email | 消费验证令牌 | 独立动作授权，204，不自动登录 |
| POST | /auth/login | 密码登录建立安全会话 | authflow或session＋CSRF，200 |
| GET | /auth/me | 本人资料与会话到期时间 | 有效会话，200 |
| POST | /auth/logout | 撤销当前会话 | 会话＋CSRF，204 |
| POST | /auth/logout-all | 验证当前密码后撤销全部会话 | 会话＋CSRF＋当前密码，204 |
| POST | /auth/password-reset-requests | 请求改密邮件 | authflow或session＋CSRF，202 |
| POST | /auth/password-reset | 凭一次性令牌改密 | 独立动作授权，204，不自动登录 |
| GET | /restaurants | 本人餐厅列表 | 会话，200，游标分页 |
| POST | /restaurants | 建店并绑定当前用户owner | 会话＋CSRF＋幂等键，201 |
| GET | /restaurants/{restaurantId} | 本人餐厅资料和ETag | 会话＋归属，200 |
| PATCH | /restaurants/{restaurantId} | 按固定白名单修改资料 | 会话＋CSRF＋归属＋If-Match，200 |
| GET | /restaurants/{restaurantId}/opening-hours | 周营业段和同一餐厅ETag | 会话＋归属，200 |
| PUT | /restaurants/{restaurantId}/opening-hours | 整体替换周营业段 | 会话＋CSRF＋归属＋If-Match，200 |

非本人归属的餐厅与不存在对象统一404，不利用403/412或细节泄露别家店的存在、版本和资料。平台支持人员另走明确、可审计的受权操作，不允许切换URL直接冒充owner。

## 4. 注册、邮箱与密码

### 注册输入

固定字段：`email`、`password`、可选`display_name`、`locale`、`terms_version`、`accepted_terms=true`。客户端先读取当前注册政策；不接受额外的role、platform_role、user_id、status或restaurant_id。

- 建议新密码长度15–128字符，不悄悄截断，不强制无意义的大小写组合或周期改密；弱/泄露密码检查及成熟哈希在技术实现阶段落实。
- 邮箱按明确策略规范化并唯一约束；不删除加号或句点，不通过注册推断顾客跨店归属。
- 合法新账号建立pending_verification、凭据、验证令牌与邮件outbox，事务提交才返回202。
- 已存在邮箱同样返回统一202，不修改其密码、不自动创建owner、不返回用户ID。
- 重发验证、找回密码也按统一响应处理不存在/不符合条件的邮箱；对外不泄露邮箱存在状态，实施时同时处理显著时间差、限流和暴力尝试。
- 条款、隐私告知不等于营销订阅同意。当前条款版本失效可以422返回版本变化，但不泄露账号状态。

### 登录与会话

邮箱不存在与密码错误统一401。只有验证密码成功后才允许提示未验证或账号不可用；未验证不能建立商家会话。JSON只返回本人资料、会话到期时间和新CSRF token，不返回session密钥或哈希。

退出必须真正撤销服务端会话；再次使用失效Cookie返回401。全设备退出要求重新验证当前密码。改密消费令牌、更新凭据和撤销全部会话必须原子完成；改密不自动登录、不借改密偷偷改变未验证邮箱状态。

邮箱验证令牌绑定purpose、当前目标邮箱和有效期，不从GET自动消费。验证后用户自行登录。令牌摘要、发送所需的短期加密材料、实际邮件发送责任遵循数据库报告。

## 5. 餐厅固定输入和草稿行为

### 可写资料

`name`、`description`、`cuisine_label`、`country_code`、`region`、`city`、`address_line1`、`address_line2`、`postal_code`、`contact_email`、`phone`、`timezone`、`currency_code`、`primary_locale`。

- 创建至少需要name和primary_locale；生成阶段的资料可稍后补齐。
- 名称最长150字符，简介2000字符，菜系100字符，地址每行200字符，电话规范国际格式。
- `PATCH`没传字段保持原值；允许为空的字段用null清除，name和primary_locale不可null，空对象不能提交。
- trim/格式/真实时区、支持币种及语言由后端验证。JSON正则只证明格式，不证明IANA时区或币种真实有效。
- `id`、`slug`、`owner`、`status`、`revision`、`reservation_enabled`、创建时间由系统负责，客户端不能直接设置；未知字段返回422，不静默忽略。
- 新店status=draft、revision=1、reservation_enabled=false；没有发布资料不会自动active或开放预订。
- 当前role=owner来自有效restaurant_members关系，不来自提交字段。

响应的readiness是派生结果，只指出当前发布缺项，不当作数据库里的永久真值或本轮“已能发布”的证明。正式网页仍需要菜单、版本校验、批准和发布模块；改草稿不直接改线上页面。

### 创建幂等

`POST /restaurants`必须传16–128字符的 `Idempotency-Key`。

创建时尚无restaurant_id，去重范围应是**当前已认证user_id＋创建动作key**。服务端保存首次输入的摘要：同键同输入返回同一餐厅的当前视图；同键不同输入409；并发重复创建最多得到一个餐厅和一条owner关系。原资源已经关闭时不因旧请求重建餐厅。

餐厅、owner、去重关联和创建审计同一事务。不能仅靠浏览器按钮disabled或先查询再无约束insert避免重复。

### 修改并发

资料和周营业段共用restaurant revision。GET返回强ETag，例如：

```text
"restaurant-rst_example_store_0001-v1"
```

PATCH/PUT携带原ETag作为 `If-Match`：缺失428，格式错误400，版本过期412；授权不通过优先404，不泄露当前版本。成功后事务内修改内容、递增revision、写审计，返回新ETag。

不能静默覆盖另一窗口的更改。超时重试遇412应重读后判断是否已写入，再决定是否重新提交，不能盲目覆盖。

## 6. 周营业时间规则

`intervals`整体替换，每段固定字段：weekday、opens_at_local、closes_at_local、closes_day_offset、accepts_requests、sort_order。

- weekday=1…7；时间精确到分钟，使用24小时制。
- closes_day_offset=0或1；例如周五18:00至周六02:00用1。
- 单段长度大于0且不超过24小时；同店区间校验必须覆盖跨午夜和周日到周一的周界。
- 一天可多段，首版最多21个周营业段；不配置某日即休息，不默认全天营业。
- 写入前餐厅timezone必须有效；`intervals=[]`可明确清空周营业段。
- 时间规则、主餐厅revision与审计同一事务，引用同一餐厅。
- 它表示营业/申请规则，不是座位库存。当前新店仍停订，accepts_requests不能绕过reservation_enabled。
- 日期例外模块和预约接口后续定义；本轮只确定周营业资料接口，不承诺已经完成容量或预订功能。

## 7. 错误、分页与返回白名单

统一错误体固定为：code、message、request_id、details（字段路径和机器原因）。错误不包含堆栈、SQL、密码、令牌、供应商密钥或别家店资料。

| 状态 | 用途 |
| --- | --- |
| 400 | JSON/参数结构错误、非法游标或ETag格式 |
| 401 | 无效会话、错误登录凭据 |
| 403 | CSRF/Origin禁止，密码验证后才可提示账号受限 |
| 404 | 对象不存在或不属于当前商家 |
| 409 | 幂等内容冲突、资源状态冲突 |
| 410 | 动作授权过期或失效 |
| 412 | If-Match过期 |
| 415 | 写入不使用application/json |
| 422 | 必填、长度、未知字段、时区/营业规则等校验失败 |
| 428 | 缺少If-Match |
| 429 | 限流，附Retry-After |
| 503 | 关键服务不可用，不用模拟结果返回成功 |

餐厅列表默认20条，最大100，按created_at和id稳定倒序；next_cursor/has_more明确下一页，游标绑定用户/查询且不可伪造。认证和商家响应Cache-Control=no-store，不由共享缓存缓存个人资料。响应仅使用契约白名单，不直接序列化数据库行。

## 8. 字段报告补充

为了让本契约的幂等与并发能够真实落库，restaurants补充4个字段；不增加逻辑表、不让商家自定义字段：

| 字段 | 作用 |
| --- | --- |
| created_by_user_id | 创建者，与有效身份外键关联，不能由客户端写 |
| create_idempotency_key | 创建请求的固定去重键 |
| create_request_fingerprint | 初始规范化输入的带版本摘要，不随资料更新改写 |
| revision | 餐厅资料及周营业段的并发版本 |

增加UNIQUE(created_by_user_id,create_idempotency_key)及对应事务约束。归属依然以restaurant_members为准，created_by_user_id不是当前权限来源。数据库报告已同步这些设计字段；这仍不表示迁移或数据库已经创建。

## 9. 静态契约检查与后续验收

### 本轮静态检查

检查脚本使用Node内置模块，无需安装依赖；验证引用、operationId、路径参数、所用schema约束及合成请求/响应示例，另检查禁止字段、空更新、格式、边界等反例。

```text
node backend/scripts/validate-contract.mjs
```

脚本只检查本契约使用的JSON Schema子集和一致性，不冒充完整OpenAPI通用验证器；不能证明真实鉴权、数据库事务、密码安全、CSRF防护或邮件可用。所有示例都是合成数据，非真实账户/密钥。

### 实施后必须验收

1. 两个真实商家分别注册、验证、登录、建店和改资料，数据重启后存在。
2. 未登录、过期/撤销会话、未验证账号和被封禁账号不能访问商家业务。
3. 跨店查询/修改404；伪造owner/status/platform_role等字段被拒绝。
4. 同一创建请求并发只建一家店；相同key不同输入409。
5. 两个窗口使用同一ETag修改时，仅第一个成功，另一个412。
6. 退出、改密、全设备撤销后旧会话真实不可用。
7. 非法时区、营业重叠、跨周界和空值边界按规则处理。
8. 邮箱验证/找回/重发不泄露账户存在；邮件失败可查、不产生假成功。
9. 登录/注册流程通过CSRF、Origin及速率控制，敏感值不进日志。
10. 备份恢复能核对身份、餐厅、owner、revision和任务事实。
