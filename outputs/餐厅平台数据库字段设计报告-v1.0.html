餐厅平台数据库字段设计报告

版本：v1.0（首版建议稿） · 日期：2026-11-14

本报告确定首版需要存储哪些数据、字段用途及约束，不创建数据库、不选择数据库厂商或技术栈。字段结构由平台固定；商家只编辑允许的内容，不修改表结构、字段类型或业务流程。设计建议仍需评审，不把未确认的业务选择写成用户已决定事项。

1. 范围与关键结论

1.1 已确认的范围

  • 商家统一注册并登录我们的平台管理；不为每家餐厅生成独立后台。
  • Agent引导商家上传菜单、图片、餐厅资料和自然语言需求；图片可由AI生成。
  • 生成可预览、可发布的HTML餐厅页面，连接我们固定的后端和真实数据库。
  • 顾客无需注册即可提交订桌信息；商家查看预订及访问数据。
  • 首版不做自动容量计算、桌位分配和拼桌；由商家自行安排。
  • 平台与生成的餐厅网站都必须满足生产级要求；前后端分离。

1.2 本报告采用的设计假设

  • 没有容量引擎，预订按“申请待确认 → 商家确认或拒绝”设计，不保证实时有位。这是建议，尚待确认。
  • 保留此前的可选顾客注册及餐厅邮件订阅能力，不默认删除需求；顾客账号底层建议统一身份、餐厅间可见数据隔离，具体体验待确认。
  • 首版正式网址以平台子域名为基线；自定义域名、营销群发和计费订阅不默认纳入。订阅邮箱与平台收费订阅不是一件事。
  • 使用固定页面契约及统一业务服务，而不是AI任意生成后端和数据库结构。

1.3 首版明确不建的数据模型

不建购物车、菜品订单、付款/订金/退款、餐桌/座位库存、容量占用、POS、积分、短信、第三方预订同步、自定义字段、复杂营销活动和企业组织层级。

1.4 总体模型

建议28个逻辑实体，分为7个数据域。认证域若采用托管认证，其中身份、会话和验证令牌可由认证服务负责；不要求手写全部物理表。其余是内容、业务与可靠性支撑，不代表增加28项商家功能。下面预订文案、状态机和对应统计均属于“人工确认”设计分支，待用户确认后冻结；表结构不是对该流程的擅自批准。固定的是数据及业务契约，不要求所有餐厅长得像同一个视觉模板。

数据域逻辑实体用途
账户与权限users、auth_identities、auth_sessions、auth_tokens、restaurant_members注册、登录、游客管理链接及商家隔离
餐厅与内容restaurants、opening_hours、opening_exceptions、assets、menus、menu_sections、menu_items餐厅资料、菜单、真实/AI素材
Agent与生成agent_sessions、agent_messages、generation_jobs引导、确认资料、生成及重试
网站与发布websites、website_versions、publish_jobs草稿、预览、正式版本与回滚
预订reservations、reservation_events申请、人工处理、取消及历史
邮件与同意email_subscriptions、subscription_events、email_outbox、email_events、email_suppressions订阅、退订、事务通知、退信抑制和可靠发送
数据与审计visit_events、daily_metrics、audit_logs访问统计、看板和安全追溯

2. 字段约定与数据归属

2.1 公共字段

除单独说明外，下列字段作为公共字段，不在每张表重复列出。

字段逻辑类型必填说明
id不透明ID是系统生成、全局唯一，不能使用连续号码作为访问凭证
created_atUTC时间点是服务端生成，不能信任客户端时间
updated_atUTC时间点是可变实体的最后修改时间
restaurant_id不透明ID/FK租户表必填餐厅数据的归属；必须从受验证的访问上下文确定

restaurant_id仅出现在餐厅级实体；users、auth_identities和auth_sessions属于全局身份域。auth_tokens与audit_logs允许明确的平台级记录。日志/事件类使用id、created_at和归属，不设置无意义的updated_at，默认只追加；依法清理个人信息是例外，不等于禁止删除。

2.2 类型与必填含义

  • ID/FK：不透明标识或外键；具体编码在技术设计时确定。
  • 文本/枚举：限定长度和允许值。本文列出的枚举不是商家可修改配置。
  • UTC时间点：存储绝对时间；餐厅当地展示使用IANA时区，如Europe/London。
  • 本地日期/时间：仅用于营业规则及用户期望时间；必须有时区才能确定实际预约时刻。
  • 整数金额：币种最小单位，结合币种的小数位规则；不默认所有币种都是两位小数，不用浮点存价格。
  • 固定JSON：严格的、带schema版本的结构；不是允许商家/模型写入任意字段的扩展口。
  • “条件”：具体条件在字段说明或约束中定义；“否”表示允许空，不表示可以不验证。“必填”默认指有效业务记录；依法匿名化后的历史记录可按清理规则置空个人信息。
  • 字段栏用“ / ”分组展示的是多个独立字段，不是一个带斜杠的列名；类型栏的分组一一对应。
  • 条款、隐私、营销同意及邮件模板的version必须能解析到不可变原文。首版可用受版本控制的固定文案目录与HTML快照，不另造可任意编辑的法律文案表；旧版本在同意证据保留期内不可删除。
  • 所有普通文本默认上限2000字符，内部ID/代码按固定协议更短；字段有特别限制则优先。JSON有schema、总大小、数组数目与嵌套深度限制，具体字节预算在实现前固定。

2.3 归属底线

每一个餐厅级外键都必须与restaurant_id配套核验。例如menu_items不能引用另一家店的menu_section，reservations不能引用另一家店的网站版本。应以复合外键或同等数据库约束实现，不能仅靠前端过滤或相信请求里的餐厅ID。

网站公开请求先根据已验证的正式域名/网站定位餐厅；商家请求根据身份及restaurant_members检查权限。统一users不代表任何商家能查看跨店顾客记录。

3. 账户与权限字段

3.1 users — 用户基础身份

商家与可选顾客账号共用身份记录，是否为商家由restaurant_members决定。游客不是伪造的用户，也不需要强行创建users。

字段类型必填说明
email文本是原始展示邮箱，最长254字符
email_normalized文本是按固定策略规范化后的登录键；不随意删加号或句点
email_verified_atUTC时间点否未验证不能认领已有游客预订
display_name文本否用户名称，最长100字符
locale文本是默认语言，使用受支持语言代码
status枚举是pending_verification / active / suspended / deleted
platform_role枚举是none / support / admin，默认none；仅受控运维授予，不接受注册或个人资料更新写入
last_login_atUTC时间点否最近成功登录
terms_version文本是注册接受的条款版本
terms_accepted_atUTC时间点是接受时间，不等于营销同意

约束：email_normalized唯一；邮箱变更须重新验证。删除后的唯一键如何释放及旧令牌如何失效须一并实现。用户字段不能自行赋予平台管理员权限。

3.2 auth_identities — 登录凭据/认证映射

字段类型必填说明
user_idID/FK是对应users
provider枚举是password / managed；具体认证方式尚未选择
provider_subject文本条件托管认证的稳定主体标识
password_hash文本条件仅自管密码时使用成熟密码哈希；绝不存明文
credential_changed_atUTC时间点是凭据最近更新

约束：provider与provider_subject组合唯一；同一用户首版只有一个有效登录方式。password模式必须有password_hash且无托管主体；managed模式必须有provider_subject且不复制托管密码到本库。

3.3 auth_sessions — 会话与撤销

字段类型必填说明
user_idID/FK是登录用户
session_secret_hash文本条件自管不透明会话/刷新令牌摘要，唯一；不存可直接使用的原令牌
provider_session_id文本条件托管服务的撤销映射，不自行制造认证状态
expires_atUTC时间点是到期时间
revoked_atUTC时间点否退出、改密、封禁或删除账号时撤销
last_seen_atUTC时间点否会话活动，用于有限期清理

只允许一种会话来源。具体刷新轮换由选定认证实现负责；旧刷新凭据撤销、重放检测及全会话失效必须纳入验收。

3.4 auth_tokens — 一次性动作与游客访问授权

这张表存令牌摘要而非明文；若认证供应商管理邮箱验证/找回密码，可只保留本平台业务链接部分。

字段类型必填说明
token_hash文本是高熵令牌的不可逆摘要，唯一
purpose枚举是verify_email / reset_password / reservation_manage / subscription_verify / subscription_unsubscribe
user_idID/FK条件verify_email、reset_password对应用户
restaurant_idID/FK条件预订/订阅令牌必须绑定餐厅
reservation_idID/FK条件reservation_manage对应唯一预订
subscription_idID/FK条件订阅确认/退订对应唯一订阅
target_email_normalized文本条件verify_email/reset_password绑定用户当前邮箱，预订/订阅链接绑定目标邮箱；变更后旧动作失效
expected_target_revision正整数订阅确认时是subscription_verify必须匹配生成时的subscription.revision；管理读取不用固定旧revision，修改另检查当前revision
expires_atUTC时间点条件验证/改密/预订管理必填；退订链接可按发送政策保持有效
used_atUTC时间点否一次性动作使用时间；订阅退订重复请求返回已退订，不恢复订阅
revoked_atUTC时间点否主动失效；预订管理授权可撤销/轮换

purpose决定允许的外键组合；不允许一个令牌同时指向用户、预订和订阅。预订管理令牌允许在有效期内多次读取，但改变状态必须防重放、幂等和版本冲突；邮件扫描器的GET请求不能直接取消预订。消费令牌与业务修改原子执行。

3.5 restaurant_members — 商家归属

字段类型必填说明
restaurant_idID/FK是餐厅归属
user_idID/FK是已存在的用户
role枚举是首版owner；manager作为后续扩展值，不默认实现员工邀请
status枚举是active / revoked

组合restaurant_id、user_id唯一；首版每店一个有效owner。注册身份不自动获得别家店权限，创建餐厅与owner关系须同一事务。平台管理员权限由独立受控权限机制提供，不能通过这里的餐厅角色越权。

4. 餐厅与内容字段

4.1 restaurants — 餐厅基本资料

字段类型必填说明
name文本是餐厅名称，最长150字符
created_by_user_idID/FK是创建者，非当前权限来源；由认证上下文写入
create_idempotency_key文本是创建餐厅请求的固定去重键，16–128字符
create_request_fingerprint文本是首次规范化输入摘要，带算法/密钥版本，不随资料更新改写
revision正整数是初始1，餐厅资料及周营业段更新共同递增，支持If-Match
slug文本是平台内标识，规范化后唯一，非授权凭证
description文本否商家确认的简介
cuisine_label文本否菜系描述，最长100字符
country_code文本发布前是固定地理代码规则
region文本否州/地区
city文本发布前是城市
address_line1文本发布前是地址
address_line2文本否补充地址
postal_code文本否不用整数，保留字母及前导零
contact_email文本发布前是餐厅公开联系方式，与登录邮箱分开
phone文本否标准国际格式，不能用整数
timezone文本发布前是有效IANA时区；预约时区不可猜测
currency_code文本菜单确认前是币种代码；修改不自动换算历史价格
primary_locale文本是首版网站语言
reservation_enabled布尔是默认false，资料完善后开启
reservation_notice文本开启预订时是清楚说明提交为申请、需餐厅确认
privacy_notice_version文本发布前是展示给顾客的隐私说明版本
status枚举是draft / active / suspended / archived

草稿允许缺少发布必需资料；发布门禁做条件校验。创建时尚无餐厅ID，UNIQUE(created_by_user_id,create_idempotency_key)保证同一用户重复创建请求不产生第二家店；同键不同首次输入拒绝，餐厅与owner关系原子提交。餐厅资料和周营业段更新必须校验并共同递增restaurant.revision。封禁/停订不自动删除预订；营业信息修改与网站发布的生效时间须明确。

2026-11-14首个接口契约补充上述4个字段，属于数据设计细化，不增加逻辑实体或表示已实际建库。

4.2 opening_hours — 每周营业规则

不用容量字段；本表用于展示营业时间及检查申请是否落在商家允许的营业段。

字段类型必填说明
restaurant_idID/FK是餐厅
weekday整数是ISO规则1=周一，7=周日
opens_at_local本地时间是开始时间
closes_at_local本地时间是结束时间
closes_day_offset整数是0=当天，1=次日；支持跨午夜
accepts_requests布尔是该营业段是否接受预订申请
sort_order整数是同日午市/晚市排序

允许一天多段，不允许同店营业区间无意重叠；无营业段表示当日休息，不假设全天营业。它不代表可用座位，不能据此显示“有位”。

4.3 opening_exceptions — 特定日期营业覆盖

字段类型必填说明
restaurant_idID/FK是餐厅
local_date本地日期是特殊营业日
is_closed布尔是true时全天关闭
intervals固定JSON是替代当天营业段：start、end、end_day_offset、accepts_requests；关闭时为空数组
note文本否节假日、临时闭店说明，最长500字符

restaurant_id、local_date唯一；有覆盖即完全替换当天周规则，不叠加。固定JSON需验证区间与跨午夜规则，不能添加任意键。

4.4 assets — 文件与图片元数据

实际文件放对象存储，不在关系数据库塞入图片或PDF二进制。

字段类型必填说明
restaurant_idID/FK是文件所有者
uploaded_by_user_idID/FK否上传人；AI产物可为空
kind枚举是menu_source / logo / restaurant_photo / dish_photo / decorative_image
origin枚举是upload / ai_generated
original_filename文本上传时是仅展示，不直接拼存储路径
storage_key文本是私有存储定位，唯一，不能保存长期签名URL
mime_type文本是服务端检测，不相信扩展名
size_bytes整数是文件大小，受限额控制
checksum文本是完整性和受控去重，不能用于跨店暴露文件存在性
width_px / height_px整数图片时是图片尺寸
alt_text文本否可访问性描述
ai_prompt文本AI时是生成说明，不包含顾客信息
ai_model_ref文本AI时是实际模型标识，不存服务密钥
merchant_approved_atUTC时间点否商家确认使用
rights_confirmed_atUTC时间点上传发布前是商家声明有权使用，不等于平台已验证版权
safety_status枚举是pending / approved / rejected
status枚举是processing / ready / failed / deleted

原菜单不公开；发布图片经审核与内容核验后从安全CDN地址提供。storage_key指向的内容与checksum不可原地替换，修改文件应创建新asset；否则回滚版本会读到新文件。删除前检查草稿与全部可回滚版本引用。可重建的签名URL不作为事实来源。AI图明确origin，不伪造“实拍”。

4.5 menus — 菜单版本性草稿容器

字段类型必填说明
restaurant_idID/FK是餐厅
title文本是如Main menu，最长100字符
source_asset_idID/FK否原PDF/图片，手工创建可为空；同店
locale文本是菜单语言
currency_code文本是菜单币种
extraction_status枚举是not_started / processing / ready / failed
confirmed_atUTC时间点否商家确认时间
confirmed_by_user_idID/FK条件confirmed_at存在时必填
revision整数是初始1，编辑后递增，防止并发覆盖
sort_order整数是显示顺序
status枚举是draft / confirmed / archived

菜单本身、任何分类/菜品的新增、删除、修改、排序和图片/价格变化，都在同一事务中递增父menus.revision，清空confirmed_at/confirmed_by_user_id并置draft；不能只改子表而仍沿用旧确认。Agent brief若引用该revision，也必须重新确认。正式网页读website_versions的已发布快照，不直接读尚未发布的最新草稿。

4.6 menu_sections — 菜品分类

字段类型必填说明
restaurant_idID/FK是餐厅
menu_idID/FK是同店菜单
title文本是前菜、主菜等，最长100字符
description文本否分类说明
sort_order整数是排序

4.7 menu_items — 菜品展示

字段类型必填说明
restaurant_idID/FK是餐厅
section_idID/FK是同店分类
name文本是最长150字符
description文本否菜品描述
price_minor非负整数否为空表示不公开价格，不等于免费
price_note文本否如Market price；不能与数字价格表达冲突
image_asset_idID/FK否同店已核验图片
labels固定列表否如商家提供的vegetarian、spicy；标签集合由平台控制
allergen_text文本否仅原菜单或商家明确提供的信息，不能自动推断
needs_review布尔是未确定内容标记，不可静默公开
is_visible布尔是显示/隐藏，不代表实时可售库存

page_key枚举是home / menu / reservation；单HTML锚点默认只计一次页面加载
referrer_host文本否仅来源主机，不存含邮箱/令牌的完整URL
traffic_source枚举否direct / search / social / other，按固定规则分类
consent_mode枚举是necessary_only / analytics_granted，取决于当地政策
visitor_day_key文本否仅获允许时使用的短期第一方标识；默认不做指纹
bot_flag布尔是基础过滤标记，不能声称完全识别机器人
excluded_reason枚举否preview / merchant_test / known_bot / invalid_context

不记录顾客邮箱、完整IP、完整查询参数、预订管理令牌或跨站追踪ID。若为防滥用短期使用IP，应在独立安全设施有限期处理，不混进营销分析表。公开统计上报仍可能伪造，要限速与过滤；不能把PV包装成精准真实人数。

9.2 daily_metrics — 按店按日访问汇总

字段类型必填说明
restaurant_idID/FK是餐厅
local_date本地日期是按metric_timezone归日
metric_timezone文本是报表时区版本；时区变更不静默改历史
page_views非负整数是有效正式page_view数
reservation_cta_clicks非负整数是有效入口点击数
estimated_daily_visitors非负整数否有足够合法标识时才有；空表示未测量，不记0
analytics_coverage固定JSON是同意/过滤覆盖，说明UV局限
metric_definition_version文本是固定指标口径
recomputed_atUTC时间点是汇总重算时间

restaurant_id、local_date、metric_timezone、metric_definition_version组合唯一。汇总可重建，不是唯一原始事实；按去重事件计算，重跑不能重复累加。保留期结束后可保留不可关联个人的历史汇总，但不能承诺无限重算历史明细。

预订看板从reservations和reservation_events查询，不把随状态变化的计数混入只增不减的访问汇总。首次曝光来源与预约提交时间是不同指标，不默认做跨站营销归因。

9.3 audit_logs — 权限与敏感操作审计

字段类型必填说明
restaurant_idID/FK条件店级操作必填；平台动作允许为空
actor_type枚举是merchant / platform_admin / system
actor_user_idID/FK条件有用户时关联；删除后可匿名化
action枚举是受控操作：publish、update_menu、decide_reservation、export等
entity_type / entity_id文本/ID是目标对象，限定受支持类型，不是通用越权查询入口
request_id文本是排查关联
outcome枚举是success / denied / failed
changed_fields固定字段名列表否只记录改了什么，不默认保存联系方式旧值
reason_code文本否平台特权访问要有明确原因

不把数据库密码、令牌、邮件正文、模型提示与敏感备注写入审计。普通商家不能修改日志。读权限、导出和平台支持访问应有最小范围与记录，不能借平台后台跨店浏览全部顾客资料。

营销订阅采用单独、默认未勾选的选项，单独调用订阅流程；不能把marketing_opt_in写成users永久布尔值，因为同意有餐厅、版本、撤回和重新订阅的历史。

11. 关系、索引与一致性

11.1 主要关系

  • users → restaurant_members → restaurants：商家权限归属。
  • restaurants → menus → menu_sections → menu_items：菜单层级。
  • restaurants → assets：原文件与图片；菜单、会话和版本只引用同店素材。
  • restaurants → agent_sessions → agent_messages；generation_jobs冻结一次输入并产出asset或website_version。
  • restaurants → websites → website_versions；publish_jobs切换当前正式版本。
  • restaurants → reservations → reservation_events；users只是可选关联，不决定业务存活。
  • restaurants → email_subscriptions → subscription_events；email_outbox → email_events。
  • websites/versions → visit_events → daily_metrics：访问事实与派生汇总分离。

11.2 必需唯一约束和查询索引

对象约束/索引作用

auth_identitiesUNIQUE(provider, provider_subject)，密码身份按用户唯一主体不能认错

唯一约束之外必须做数据库CHECK、外键与长度限制。所有同店父子关系有restaurant_id复合约束；特殊全局用户关联有独立权限检查。业务型JSON由后端严格校验，不用JSON取代核心关系和权限键。

11.3 幂等与清理的补充规则

每张业务表的idempotency_key仅在该表、该restaurant内唯一，generation_jobs的kind和publish_jobs的action包含在服务端request_fingerprint里。相同键相同原始摘要返回原结果，相同键不同输入拒绝，不能拿修改后的reservations行比较初始提交。预约动作另以reservation_id+request_id及action_fingerprint判重。摘要携带算法/密钥版本前缀；关联顾客内容的摘要使用带密钥方案，不保留可枚举的明文哈希。活跃业务期保留去重依据；预约匿名化后旧动作/提交授权必须拒绝，清理原请求摘要，必要时仅保留无内容的去重墓碑及ID，避免旧请求重新创建业务。预览使用隔离环境/预览接口，正式预订表不接收测试记录，统计的excluded_reason由服务端上下文确定，不信任客户端自称“测试”。

增加约束：subscription_events唯一(subscription_id,subscription_revision)；reservation_events唯一(reservation_id,request_id)；email_suppressions唯一(email_key_version,email_key_hmac)。预约状态统计按指定报表时区计算，查询必须显示使用的时区；原始访问汇总使用事件时区快照，改时区后历史汇总不默默移日。

11.4 必须原子或可恢复的动作

  1. 创建餐厅与owner关系；不能产生无归属餐厅。
  2. 菜单确认与revision检查；编辑后重新确认。
  3. 创建/确认/拒绝/取消预订＋变更事件＋邮件入队。
  4. 一次性授权消费＋对应动作；旧revision不能覆盖新状态。
  5. 订阅状态变化＋同意事件；撤回立即阻止后续营销。
  6. 网站正式指针切换与revision检查；外部部署失败保留旧站并可对账。
  7. 供应商事件去重及抑制更新；回调乱序不取消已知投诉/硬退信状态。
  8. 查询/导出先检查用户、角色及restaurant归属，不先取全表再前端过滤。

12. 看板指标口径

指标定义/来源不代表什么
页面浏览量PV有效正式页面加载事件，排除预览/已知机器人真实独立人数、所有访问都可精准追踪
当日估计访客UV当天合法第一方标识去重，可空月UV不能简单把每日UV相加
预订申请数按created_at归日的已提交申请；排除测试成功订位数
已确认申请数对指定申请时间段的记录，当前status=confirmed确认发生日计数，两者不能混用
待确认/拒绝/取消数同一申请创建区间内的当前状态历史某日状态，若要历史需从事件重建
预约人数按requested_start_at的到店日期汇总confirmed的party_size实际到店、已消费收入
有效邮件订阅数当前subscribed且未抑制所有注册用户或所有预约邮箱

“申请提交率”如展示，须定义相同餐厅、时期和来源覆盖的口径；首版不把预约申请数/PV当成严谨的人级转化率，电话录入也不能算网页转化。访问未授权、机器人过滤和跨日申请都会影响数据。

13. 不存什么、存在哪里

13.1 数据库与外部存储分工

  • 数据库：身份映射、归属、菜单结构、确认事实、固定快照、版本引用、预订、订阅、任务与指标。
  • 对象存储：原始PDF、图片、生成HTML、必要的构建产物；使用storage_key与校验摘要关联。
  • 密钥管理：数据库密码、模型API密钥、邮件密钥、加密密钥；绝不放在商家表、HTML或普通日志里。
  • 可短期重建数据：预览签名URL、任务租约、限流状态。它们不作为长期业务事实。

13.2 不收集/不持久化

顾客支付卡资料、政府证件、生日、精确定位、跨店行为画像、隐藏模型推理、无限期完整IP、管理令牌明文、未授权通讯录；首版不需要这些。顾客备注可能含敏感信息，限制提示、权限和保留，不能把备注发给建站模型。

13.3 保留与删除建议（待首发国家及政策确认）

数据建议基线清理要求
预订联系信息max(requested_start_at、最后处理/取消时间)后90天为初始产品建议，不是法律结论；未处理pending先按明确超时政策关闭没有实际到店记录，不用“服务完成”虚构清理起点；到期置空个人字段，保留必要非个人计数
原始访问事件30天清理标识和事件；只保留不可关联个人的日汇总
Agent对话与失败中间稿完成后90天保留经确认资料，删多余原始对话和临时内容
认证/业务令牌按用途短期到期，退订令牌另按邮件有效期改密/确认一次性令牌使用后清理；预订管理到期后清理；有效退订链接不按一次性确认规则误删
邮件正文/payload发出或失效后30天以内短期动作密文尽快删除；保留必要状态而非永久全文
审计180天的起始建议不含多余PII；监管/合同要求另外核定
营销同意/抑制按有效授权、争议与发送政策设定保留最小撤回/抑制证据，不能删除后重新导入发送
发布版本和素材当前版本＋有限可回滚版本先检查引用；删HTML版本不删预订事实

用户删除：删除身份凭据/会话/令牌，users保留不含邮箱/姓名的deleted身份墓碑以维持必填历史外键；活跃身份必须有邮箱，deleted身份邮箱置空，并仅对非空登录键做唯一约束。customer_user_id、可选操作者ID可置空，不能让用户删除级联摧毁菜单、网站或预约。商家owner删除前必须先移交或关闭餐厅。

预约匿名化置空guest_name、guest_email、guest_email_normalized、guest_phone、guest_note、internal_note、customer_user_id，写anonymized_at并撤销管理令牌；有效业务记录字段必填，anonymized_at非空的历史行允许这些字段为空。事件JSON、发送payload和引用快照也同步清理相关个人信息，预约日期/人数/状态的必要计数按明确目的保留。订阅删除须保留受保护的最小撤回/抑制证据，不能清理后自动恢复发送。有限期同意证据不能无限保留。匿名化不能被全量同步/模型重新生成逆向恢复。

商家关闭：停止公开网站与新申请、处理尚未完成预订、再执行分层数据清理。备份有独立保留期和恢复后的删除重放机制；不能承诺删除即时消除所有历史备份。

14. 首版验收与待确认项

14.1 数据验收

  • 商家注册、餐厅创建、菜单确认、生成、发布均有真实可恢复记录。
  • 跨店读取和引用失败；游客链接不能查看别人预订。
  • 重复提交产生一笔申请；并发商家处理只接受一个revision，通知跟随最终事件。
  • 生成、发布重试不覆盖旧正式站，不修改已有预订和邮件订阅。
  • 预览不进入reservations、email_outbox和正式visit_events指标。
  • 客户端伪造status、restaurant_id、user_id无法越权。
  • 用户注册不自动变成营销subscribed，退订后旧确认链接不能恢复授权。
  • 邮件失败可查；外部供应商超时不能盲目重复发送。
  • 服务重启及备份恢复后，关联、索引、网站引用、预订与同意历史可以核对。

14.2 尚需确认的产品选择

  1. 无容量管理时，是否采用人工确认申请？本稿按此设计。
  2. 保留此前顾客可选注册需求；仅账号体验是否跨店统一、游客记录如何验证认领需确认，不擅自将注册移出首版。
  3. 邮件仅做事务通知＋订阅收集，还是首版开放营销群发？本稿不默认加群发活动表。
  4. 游客是否先验证邮箱？本稿预留验证字段，但不把无注册等同无验证。
  5. 自定义域名、具体取消/改约规则和保留期限，后续确认后冻结；未确认不影响已确定核心字段。

15. 最终建议

把“商家能填的固定内容”“AI提取草稿”“已发布网页快照”“真实预订和订阅数据”分开保存。首版固定数据字段和业务契约，视觉设计可变化，后端集中负责权限和业务；让模型生成页面，不让模型定义表结构或决定预订状态。

最重要的长期字段是restaurant_id、稳定业务ID、内容revision、网站版本、预订状态/事件、营销同意历史及幂等键。它们让第一版即便功能少，也具备隔离、可靠更新、失败重试和后续扩展的基础。

本报告是首版数据设计建议。已确认需求与待确认流程分开标注；生产级验收需在实施阶段取得测试、权限隔离及恢复证据。
