# 餐厅平台数据库字段设计报告

版本：v1.0（首版建议稿） · 日期：2026-11-14

> 本报告确定首版需要存储哪些数据、字段用途及约束，不创建数据库、不选择数据库厂商或技术栈。字段结构由平台固定；商家只编辑允许的内容，不修改表结构、字段类型或业务流程。设计建议仍需评审，不把未确认的业务选择写成用户已决定事项。

## 1. 范围与关键结论

### 1.1 已确认的范围

- 商家统一注册并登录我们的平台管理；不为每家餐厅生成独立后台。
- Agent引导商家上传菜单、图片、餐厅资料和自然语言需求；图片可由AI生成。
- 生成可预览、可发布的HTML餐厅页面，连接我们固定的后端和真实数据库。
- 顾客无需注册即可提交订桌信息；商家查看预订及访问数据。
- 首版不做自动容量计算、桌位分配和拼桌；由商家自行安排。
- 平台与生成的餐厅网站都必须满足生产级要求；前后端分离。

### 1.2 本报告采用的设计假设

- 没有容量引擎，预订按“申请待确认 → 商家确认或拒绝”设计，不保证实时有位。这是建议，尚待确认。
- 保留此前的可选顾客注册及餐厅邮件订阅能力，不默认删除需求；顾客账号底层建议统一身份、餐厅间可见数据隔离，具体体验待确认。
- 首版正式网址以平台子域名为基线；自定义域名、营销群发和计费订阅不默认纳入。订阅邮箱与平台收费订阅不是一件事。
- 使用固定页面契约及统一业务服务，而不是AI任意生成后端和数据库结构。

### 1.3 首版明确不建的数据模型

不建购物车、菜品订单、付款/订金/退款、餐桌/座位库存、容量占用、POS、积分、短信、第三方预订同步、自定义字段、复杂营销活动和企业组织层级。

### 1.4 总体模型

建议28个逻辑实体，分为7个数据域。认证域若采用托管认证，其中身份、会话和验证令牌可由认证服务负责；不要求手写全部物理表。其余是内容、业务与可靠性支撑，不代表增加28项商家功能。下面预订文案、状态机和对应统计均属于“人工确认”设计分支，待用户确认后冻结；表结构不是对该流程的擅自批准。固定的是数据及业务契约，不要求所有餐厅长得像同一个视觉模板。

| 数据域 | 逻辑实体 | 用途 |
| --- | --- | --- |
| 账户与权限 | users、auth_identities、auth_sessions、auth_tokens、restaurant_members | 注册、登录、游客管理链接及商家隔离 |
| 餐厅与内容 | restaurants、opening_hours、opening_exceptions、assets、menus、menu_sections、menu_items | 餐厅资料、菜单、真实/AI素材 |
| Agent与生成 | agent_sessions、agent_messages、generation_jobs | 引导、确认资料、生成及重试 |
| 网站与发布 | websites、website_versions、publish_jobs | 草稿、预览、正式版本与回滚 |
| 预订 | reservations、reservation_events | 申请、人工处理、取消及历史 |
| 邮件与同意 | email_subscriptions、subscription_events、email_outbox、email_events、email_suppressions | 订阅、退订、事务通知、退信抑制和可靠发送 |
| 数据与审计 | visit_events、daily_metrics、audit_logs | 访问统计、看板和安全追溯 |

## 2. 字段约定与数据归属

### 2.1 公共字段

除单独说明外，下列字段作为公共字段，不在每张表重复列出。

| 字段 | 逻辑类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| id | 不透明ID | 是 | 系统生成、全局唯一，不能使用连续号码作为访问凭证 |
| created_at | UTC时间点 | 是 | 服务端生成，不能信任客户端时间 |
| updated_at | UTC时间点 | 是 | 可变实体的最后修改时间 |
| restaurant_id | 不透明ID/FK | 租户表必填 | 餐厅数据的归属；必须从受验证的访问上下文确定 |

restaurant_id仅出现在餐厅级实体；users、auth_identities和auth_sessions属于全局身份域。auth_tokens与audit_logs允许明确的平台级记录。日志/事件类使用id、created_at和归属，不设置无意义的updated_at，默认只追加；依法清理个人信息是例外，不等于禁止删除。

### 2.2 类型与必填含义

- ID/FK：不透明标识或外键；具体编码在技术设计时确定。
- 文本/枚举：限定长度和允许值。本文列出的枚举不是商家可修改配置。
- UTC时间点：存储绝对时间；餐厅当地展示使用IANA时区，如Europe/London。
- 本地日期/时间：仅用于营业规则及用户期望时间；必须有时区才能确定实际预约时刻。
- 整数金额：币种最小单位，结合币种的小数位规则；不默认所有币种都是两位小数，不用浮点存价格。
- 固定JSON：严格的、带schema版本的结构；不是允许商家/模型写入任意字段的扩展口。
- “条件”：具体条件在字段说明或约束中定义；“否”表示允许空，不表示可以不验证。“必填”默认指有效业务记录；依法匿名化后的历史记录可按清理规则置空个人信息。
- 字段栏用“ / ”分组展示的是多个独立字段，不是一个带斜杠的列名；类型栏的分组一一对应。
- 条款、隐私、营销同意及邮件模板的version必须能解析到不可变原文。首版可用受版本控制的固定文案目录与HTML快照，不另造可任意编辑的法律文案表；旧版本在同意证据保留期内不可删除。
- 所有普通文本默认上限2000字符，内部ID/代码按固定协议更短；字段有特别限制则优先。JSON有schema、总大小、数组数目与嵌套深度限制，具体字节预算在实现前固定。

### 2.3 归属底线

每一个餐厅级外键都必须与restaurant_id配套核验。例如menu_items不能引用另一家店的menu_section，reservations不能引用另一家店的网站版本。应以复合外键或同等数据库约束实现，不能仅靠前端过滤或相信请求里的餐厅ID。

网站公开请求先根据已验证的正式域名/网站定位餐厅；商家请求根据身份及restaurant_members检查权限。统一users不代表任何商家能查看跨店顾客记录。

## 3. 账户与权限字段

### 3.1 users — 用户基础身份

商家与可选顾客账号共用身份记录，是否为商家由restaurant_members决定。游客不是伪造的用户，也不需要强行创建users。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| email | 文本 | 是 | 原始展示邮箱，最长254字符 |
| email_normalized | 文本 | 是 | 按固定策略规范化后的登录键；不随意删加号或句点 |
| email_verified_at | UTC时间点 | 否 | 未验证不能认领已有游客预订 |
| display_name | 文本 | 否 | 用户名称，最长100字符 |
| locale | 文本 | 是 | 默认语言，使用受支持语言代码 |
| status | 枚举 | 是 | pending_verification / active / suspended / deleted |
| platform_role | 枚举 | 是 | none / support / admin，默认none；仅受控运维授予，不接受注册或个人资料更新写入 |
| last_login_at | UTC时间点 | 否 | 最近成功登录 |
| terms_version | 文本 | 是 | 注册接受的条款版本 |
| terms_accepted_at | UTC时间点 | 是 | 接受时间，不等于营销同意 |

约束：email_normalized唯一；邮箱变更须重新验证。删除后的唯一键如何释放及旧令牌如何失效须一并实现。用户字段不能自行赋予平台管理员权限。

### 3.2 auth_identities — 登录凭据/认证映射

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| user_id | ID/FK | 是 | 对应users |
| provider | 枚举 | 是 | password / managed；具体认证方式尚未选择 |
| provider_subject | 文本 | 条件 | 托管认证的稳定主体标识 |
| password_hash | 文本 | 条件 | 仅自管密码时使用成熟密码哈希；绝不存明文 |
| credential_changed_at | UTC时间点 | 是 | 凭据最近更新 |

约束：provider与provider_subject组合唯一；同一用户首版只有一个有效登录方式。password模式必须有password_hash且无托管主体；managed模式必须有provider_subject且不复制托管密码到本库。

### 3.3 auth_sessions — 会话与撤销

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| user_id | ID/FK | 是 | 登录用户 |
| session_secret_hash | 文本 | 条件 | 自管不透明会话/刷新令牌摘要，唯一；不存可直接使用的原令牌 |
| provider_session_id | 文本 | 条件 | 托管服务的撤销映射，不自行制造认证状态 |
| expires_at | UTC时间点 | 是 | 到期时间 |
| revoked_at | UTC时间点 | 否 | 退出、改密、封禁或删除账号时撤销 |
| last_seen_at | UTC时间点 | 否 | 会话活动，用于有限期清理 |

只允许一种会话来源。具体刷新轮换由选定认证实现负责；旧刷新凭据撤销、重放检测及全会话失效必须纳入验收。

### 3.4 auth_tokens — 一次性动作与游客访问授权

这张表存令牌摘要而非明文；若认证供应商管理邮箱验证/找回密码，可只保留本平台业务链接部分。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| token_hash | 文本 | 是 | 高熵令牌的不可逆摘要，唯一 |
| purpose | 枚举 | 是 | verify_email / reset_password / reservation_manage / subscription_verify / subscription_unsubscribe |
| user_id | ID/FK | 条件 | verify_email、reset_password对应用户 |
| restaurant_id | ID/FK | 条件 | 预订/订阅令牌必须绑定餐厅 |
| reservation_id | ID/FK | 条件 | reservation_manage对应唯一预订 |
| subscription_id | ID/FK | 条件 | 订阅确认/退订对应唯一订阅 |
| target_email_normalized | 文本 | 条件 | verify_email/reset_password绑定用户当前邮箱，预订/订阅链接绑定目标邮箱；变更后旧动作失效 |
| expected_target_revision | 正整数 | 订阅确认时是 | subscription_verify必须匹配生成时的subscription.revision；管理读取不用固定旧revision，修改另检查当前revision |
| expires_at | UTC时间点 | 条件 | 验证/改密/预订管理必填；退订链接可按发送政策保持有效 |
| used_at | UTC时间点 | 否 | 一次性动作使用时间；订阅退订重复请求返回已退订，不恢复订阅 |
| revoked_at | UTC时间点 | 否 | 主动失效；预订管理授权可撤销/轮换 |

purpose决定允许的外键组合；不允许一个令牌同时指向用户、预订和订阅。预订管理令牌允许在有效期内多次读取，但改变状态必须防重放、幂等和版本冲突；邮件扫描器的GET请求不能直接取消预订。消费令牌与业务修改原子执行。

### 3.5 restaurant_members — 商家归属

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| restaurant_id | ID/FK | 是 | 餐厅归属 |
| user_id | ID/FK | 是 | 已存在的用户 |
| role | 枚举 | 是 | 首版owner；manager作为后续扩展值，不默认实现员工邀请 |
| status | 枚举 | 是 | active / revoked |

组合restaurant_id、user_id唯一；首版每店一个有效owner。注册身份不自动获得别家店权限，创建餐厅与owner关系须同一事务。平台管理员权限由独立受控权限机制提供，不能通过这里的餐厅角色越权。

## 4. 餐厅与内容字段

### 4.1 restaurants — 餐厅基本资料

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| name | 文本 | 是 | 餐厅名称，最长150字符 |
| created_by_user_id | ID/FK | 是 | 创建者，非当前权限来源；由认证上下文写入 |
| create_idempotency_key | 文本 | 是 | 创建餐厅请求的固定去重键，16–128字符 |
| create_request_fingerprint | 文本 | 是 | 首次规范化输入摘要，带算法/密钥版本，不随资料更新改写 |
| revision | 正整数 | 是 | 初始1，餐厅资料及周营业段更新共同递增，支持If-Match |
| slug | 文本 | 是 | 平台内标识，规范化后唯一，非授权凭证 |
| description | 文本 | 否 | 商家确认的简介 |
| cuisine_label | 文本 | 否 | 菜系描述，最长100字符 |
| country_code | 文本 | 发布前是 | 固定地理代码规则 |
| region | 文本 | 否 | 州/地区 |
| city | 文本 | 发布前是 | 城市 |
| address_line1 | 文本 | 发布前是 | 地址 |
| address_line2 | 文本 | 否 | 补充地址 |
| postal_code | 文本 | 否 | 不用整数，保留字母及前导零 |
| contact_email | 文本 | 发布前是 | 餐厅公开联系方式，与登录邮箱分开 |
| phone | 文本 | 否 | 标准国际格式，不能用整数 |
| timezone | 文本 | 发布前是 | 有效IANA时区；预约时区不可猜测 |
| currency_code | 文本 | 菜单确认前是 | 币种代码；修改不自动换算历史价格 |
| primary_locale | 文本 | 是 | 首版网站语言 |
| reservation_enabled | 布尔 | 是 | 默认false，资料完善后开启 |
| reservation_notice | 文本 | 开启预订时是 | 清楚说明提交为申请、需餐厅确认 |
| privacy_notice_version | 文本 | 发布前是 | 展示给顾客的隐私说明版本 |
| status | 枚举 | 是 | draft / active / suspended / archived |

草稿允许缺少发布必需资料；发布门禁做条件校验。创建时尚无餐厅ID，UNIQUE(created_by_user_id,create_idempotency_key)保证同一用户重复创建请求不产生第二家店；同键不同首次输入拒绝，餐厅与owner关系原子提交。餐厅资料和周营业段更新必须校验并共同递增restaurant.revision。封禁/停订不自动删除预订；营业信息修改与网站发布的生效时间须明确。

2026-11-14首个接口契约补充上述4个字段，属于数据设计细化，不增加逻辑实体或表示已实际建库。

### 4.2 opening_hours — 每周营业规则

不用容量字段；本表用于展示营业时间及检查申请是否落在商家允许的营业段。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| restaurant_id | ID/FK | 是 | 餐厅 |
| weekday | 整数 | 是 | ISO规则1=周一，7=周日 |
| opens_at_local | 本地时间 | 是 | 开始时间 |
| closes_at_local | 本地时间 | 是 | 结束时间 |
| closes_day_offset | 整数 | 是 | 0=当天，1=次日；支持跨午夜 |
| accepts_requests | 布尔 | 是 | 该营业段是否接受预订申请 |
| sort_order | 整数 | 是 | 同日午市/晚市排序 |

允许一天多段，不允许同店营业区间无意重叠；无营业段表示当日休息，不假设全天营业。它不代表可用座位，不能据此显示“有位”。

### 4.3 opening_exceptions — 特定日期营业覆盖

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| restaurant_id | ID/FK | 是 | 餐厅 |
| local_date | 本地日期 | 是 | 特殊营业日 |
| is_closed | 布尔 | 是 | true时全天关闭 |
| intervals | 固定JSON | 是 | 替代当天营业段：start、end、end_day_offset、accepts_requests；关闭时为空数组 |
| note | 文本 | 否 | 节假日、临时闭店说明，最长500字符 |

restaurant_id、local_date唯一；有覆盖即完全替换当天周规则，不叠加。固定JSON需验证区间与跨午夜规则，不能添加任意键。

### 4.4 assets — 文件与图片元数据

实际文件放对象存储，不在关系数据库塞入图片或PDF二进制。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| restaurant_id | ID/FK | 是 | 文件所有者 |
| uploaded_by_user_id | ID/FK | 否 | 上传人；AI产物可为空 |
| kind | 枚举 | 是 | menu_source / logo / restaurant_photo / dish_photo / decorative_image |
| origin | 枚举 | 是 | upload / ai_generated |
| original_filename | 文本 | 上传时是 | 仅展示，不直接拼存储路径 |
| storage_key | 文本 | 是 | 私有存储定位，唯一，不能保存长期签名URL |
| mime_type | 文本 | 是 | 服务端检测，不相信扩展名 |
| size_bytes | 整数 | 是 | 文件大小，受限额控制 |
| checksum | 文本 | 是 | 完整性和受控去重，不能用于跨店暴露文件存在性 |
| width_px / height_px | 整数 | 图片时是 | 图片尺寸 |
| alt_text | 文本 | 否 | 可访问性描述 |
| ai_prompt | 文本 | AI时是 | 生成说明，不包含顾客信息 |
| ai_model_ref | 文本 | AI时是 | 实际模型标识，不存服务密钥 |
| merchant_approved_at | UTC时间点 | 否 | 商家确认使用 |
| rights_confirmed_at | UTC时间点 | 上传发布前是 | 商家声明有权使用，不等于平台已验证版权 |
| safety_status | 枚举 | 是 | pending / approved / rejected |
| status | 枚举 | 是 | processing / ready / failed / deleted |

原菜单不公开；发布图片经审核与内容核验后从安全CDN地址提供。storage_key指向的内容与checksum不可原地替换，修改文件应创建新asset；否则回滚版本会读到新文件。删除前检查草稿与全部可回滚版本引用。可重建的签名URL不作为事实来源。AI图明确origin，不伪造“实拍”。

### 4.5 menus — 菜单版本性草稿容器

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| restaurant_id | ID/FK | 是 | 餐厅 |
| title | 文本 | 是 | 如Main menu，最长100字符 |
| source_asset_id | ID/FK | 否 | 原PDF/图片，手工创建可为空；同店 |
| locale | 文本 | 是 | 菜单语言 |
| currency_code | 文本 | 是 | 菜单币种 |

| recipient_email_key / email_key_version | 文本/整数 | 是 | 规范化地址的带密钥HMAC及版本，用于最小化抑制匹配，不向商家公开 |
| user_id | ID/FK | 否 | 平台账户通知 |
| reservation_id | ID/FK | 否 | 同店预订通知 |
| subscription_id | ID/FK | 营销时是 | 同店有效订阅 |
| payload | 固定JSON | 是 | 模板必需的姓名/时间/品牌字段，非任意HTML或密钥 |
| sensitive_payload_ciphertext | 加密密文 | 否 | 如一次性动作链接的短期发送材料；只允许发送进程解密，发出或到期删除 |
| dedupe_key | 文本 | 是 | 类别+业务对象+事件revision+模板版本，唯一 |
| scheduled_at | UTC时间点 | 是 | 提醒调度及发送时间 |
| status | 枚举 | 是 | queued / sending / accepted / failed / cancelled / suppressed |
| attempt_count / max_attempts | 整数 | 是 | 重试上限 |
| available_at / lease_expires_at | UTC时间点 | 是/否 | 调度/租约 |
| provider_message_id | 文本 | 否 | 供应商接受后的标识，非真实送达证明 |
| accepted_at | UTC时间点 | 否 | 供应商接受时间 |
| last_error_code | 文本 | 否 | 脱敏故障 |

数据组合CHECK：restaurant_id为空的任务只能是平台transactional，必须有user_id且reservation_id/subscription_id为空；餐厅任务必须有restaurant_id，全部业务引用同店，marketing必须有subscription_id。email_events的归属与对应任务严格一致，不利用可空复合外键跳过检查。

发送前重新检查订阅及平台email_suppressions，已退订营销任务取消；必要事务邮件与营销退订分离，但硬退信/投诉必须按供应商及平台政策处理。accepted不等于delivered。定时提醒发送前检查预约仍有效、revision一致；改约/取消使旧提醒失效。

单靠outbox不能保证外部邮件绝不重复：优先使用供应商幂等键；网络超时按provider_message_id/dedupe_key对账，不盲目再发。动作令牌原文不得进入普通日志；若重试所需材料需暂存，采用密钥在库外管理的短期加密字段。

### 8.4 email_events — 供应商回执

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| email_outbox_id | ID/FK | 是 | 对应发送任务，餐厅归属随任务验证 |
| restaurant_id | ID/FK | 条件 | 跟任务归属一致 |
| provider_event_id | 文本 | 是 | 供应商事件去重，唯一/带provider前缀 |
| provider_message_id | 文本 | 是 | 与outbox匹配 |
| event_type | 枚举 | 是 | delivered / deferred / hard_bounce / soft_bounce / complaint |
| occurred_at | UTC时间点 | 是 | 供应商事件时间；created_at是平台接收时间 |
| reason_code | 文本 | 否 | 机器分类，不存完整邮件正文 |
| payload_digest | 文本 | 否 | 有需要时验证事件完整性；不保存整段原始PII返回 |

必须验证回调签名、重放和所属provider消息。事件可能重复、乱序；不要只覆盖一个字段丢失投诉。hard_bounce/complaint需要影响对应地址的发送抑制，平台级供应商抑制优先，不能只改单一营销任务。

首版没有营销群发表。订阅列表与发送机制先具备，是否提供商家群发入口待确认；若确认，另加campaigns/recipients及审批、限额，不往email_outbox塞任意内容替代活动模型。

### 8.5 email_suppressions — 最小地址抑制账本

平台级安全发送数据，不是供商家查询的跨店用户画像。它覆盖无营销订阅的事务收件地址；删除旧邮件事件后仍能阻止给投诉/硬退信地址发送。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| email_key_hmac | 文本 | 是 | 规范化地址的带密钥HMAC，不保留明文；密钥在库外 |
| email_key_version | 正整数 | 是 | HMAC版本，轮换需迁移或双版本查验，不能使旧抑制失效 |
| reason | 枚举 | 是 | hard_bounce / complaint / admin_block |
| source_outbox_id | ID/FK | 否 | 证据来源，可按保留政策置空 |
| active | 布尔 | 是 | 是否仍阻止发送 |
| activated_at | UTC时间点 | 是 | 启用时间 |
| released_at | UTC时间点 | 否 | 受控解除时间 |
| release_reason_code | 文本 | 否 | 人工验证解除原因 |

UNIQUE(email_key_version,email_key_hmac)。发送入口对所有类别查验，本地与供应商抑制都必须遵守。重新订阅不得自动解除投诉/硬退信；只有受控验证流程可解除，记录审计。HMAC仍属受保护的可关联数据，并非无需保留政策的匿名数据。

| page_key | 枚举 | 是 | home / menu / reservation；单HTML锚点默认只计一次页面加载 |

### 9.2 daily_metrics — 按店按日访问汇总

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| restaurant_id | ID/FK | 是 | 餐厅 |
| local_date | 本地日期 | 是 | 按metric_timezone归日 |
| metric_timezone | 文本 | 是 | 报表时区版本；时区变更不静默改历史 |

| reservation_cta_clicks | 非负整数 | 是 | 有效入口点击数 |

| analytics_coverage | 固定JSON | 是 | 同意/过滤覆盖，说明UV局限 |

restaurant_id、local_date、metric_timezone、metric_definition_version组合唯一。汇总可重建，不是唯一原始事实；按去重事件计算，重跑不能重复累加。保留期结束后可保留不可关联个人的历史汇总，但不能承诺无限重算历史明细。

## 11. 关系、索引与一致性

### 11.1 主要关系

- users → restaurant_members → restaurants：商家权限归属。
- restaurants → menus → menu_sections → menu_items：菜单层级。
- restaurants → assets：原文件与图片；菜单、会话和版本只引用同店素材。
- restaurants → agent_sessions → agent_messages；generation_jobs冻结一次输入并产出asset或website_version。
- restaurants → websites → website_versions；publish_jobs切换当前正式版本。
- restaurants → reservations → reservation_events；users只是可选关联，不决定业务存活。
- restaurants → email_subscriptions → subscription_events；email_outbox → email_events。
- websites/versions → visit_events → daily_metrics：访问事实与派生汇总分离。

### 11.2 必需唯一约束和查询索引

| 对象 | 约束/索引 | 作用 |
| --- | --- | --- |
| users | UNIQUE(email_normalized) | 注册去重 |
| auth_identities | UNIQUE(provider, provider_subject)，密码身份按用户唯一 | 主体不能认错 |
| auth_sessions | user_id + revoked_at + expires_at | 退出/封禁批量撤销 |
| auth_tokens | UNIQUE(token_hash)，expires_at，绑定对象 | 动作授权与清理 |
| restaurant_members | UNIQUE(restaurant_id,user_id)，user_id+status | 商家店铺列表与授权 |
| opening_exceptions | UNIQUE(restaurant_id,local_date) | 不重复覆盖 |
| menu_sections / menu_items | 餐厅+父级+sort_order | 内容查询；父级复合FK |
| agent_messages | UNIQUE(session_id,sequence_no) | 消息顺序与重试 |
| generation_jobs / publish_jobs | UNIQUE(restaurant_id,idempotency_key)，status+available_at | 防重复与任务调度 |
| websites | UNIQUE(restaurant_id)，UNIQUE(public_slug) | 一店一站与路由 |
| website_versions | UNIQUE(website_id,version_no) | 版本可定位 |
| reservations | UNIQUE(restaurant_id,idempotency_key)，餐厅+开始时间，餐厅+状态+created_at | 防重复、按到店日/申请日列表 |
| reservations | customer_user_id+created_at；邮箱仅供受权商家检索 | 顾客个人记录，不构成访客权限 |
| reservation_events | UNIQUE(reservation_id,reservation_revision) | 事件与状态版本一一对应 |
| email_subscriptions | UNIQUE(restaurant_id,email_normalized) | 按餐厅管理订阅 |
| email_outbox | UNIQUE(dedupe_key)，status+available_at，业务对象+模板 | 通知防重复与排查 |
| email_events | UNIQUE(provider前缀+provider_event_id) | 回调重放去重 |
| visit_events | UNIQUE(event_id)，餐厅+occurred_at | 事件去重与按日查询 |
| audit_logs | 餐厅+created_at，request_id，actor_user_id+created_at | 排查与审计 |

唯一约束之外必须做数据库CHECK、外键与长度限制。所有同店父子关系有restaurant_id复合约束；特殊全局用户关联有独立权限检查。业务型JSON由后端严格校验，不用JSON取代核心关系和权限键。

### 11.3 幂等与清理的补充规则

每张业务表的idempotency_key仅在该表、该restaurant内唯一，generation_jobs的kind和publish_jobs的action包含在服务端request_fingerprint里。相同键相同原始摘要返回原结果，相同键不同输入拒绝，不能拿修改后的reservations行比较初始提交。预约动作另以reservation_id+request_id及action_fingerprint判重。摘要携带算法/密钥版本前缀；关联顾客内容的摘要使用带密钥方案，不保留可枚举的明文哈希。活跃业务期保留去重依据；预约匿名化后旧动作/提交授权必须拒绝，清理原请求摘要，必要时仅保留无内容的去重墓碑及ID，避免旧请求重新创建业务。预览使用隔离环境/预览接口，正式预订表不接收测试记录，统计的excluded_reason由服务端上下文确定，不信任客户端自称“测试”。

增加约束：subscription_events唯一(subscription_id,subscription_revision)；reservation_events唯一(reservation_id,request_id)；email_suppressions唯一(email_key_version,email_key_hmac)。预约状态统计按指定报表时区计算，查询必须显示使用的时区；原始访问汇总使用事件时区快照，改时区后历史汇总不默默移日。

### 11.4 必须原子或可恢复的动作

1. 创建餐厅与owner关系；不能产生无归属餐厅。
2. 菜单确认与revision检查；编辑后重新确认。
3. 创建/确认/拒绝/取消预订＋变更事件＋邮件入队。
4. 一次性授权消费＋对应动作；旧revision不能覆盖新状态。
5. 订阅状态变化＋同意事件；撤回立即阻止后续营销。
6. 网站正式指针切换与revision检查；外部部署失败保留旧站并可对账。
7. 供应商事件去重及抑制更新；回调乱序不取消已知投诉/硬退信状态。
8. 查询/导出先检查用户、角色及restaurant归属，不先取全表再前端过滤。

## 12. 看板指标口径

| 指标 | 定义/来源 | 不代表什么 |
| --- | --- | --- |
| 页面浏览量PV | 有效正式页面加载事件，排除预览/已知机器人 | 真实独立人数、所有访问都可精准追踪 |
| 当日估计访客UV | 当天合法第一方标识去重，可空 | 月UV不能简单把每日UV相加 |
| 预订申请数 | 按created_at归日的已提交申请；排除测试 | 成功订位数 |
| 已确认申请数 | 对指定申请时间段的记录，当前status=confirmed | 确认发生日计数，两者不能混用 |
| 待确认/拒绝/取消数 | 同一申请创建区间内的当前状态 | 历史某日状态，若要历史需从事件重建 |
| 预约人数 | 按requested_start_at的到店日期汇总confirmed的party_size | 实际到店、已消费收入 |
| 有效邮件订阅数 | 当前subscribed且未抑制 | 所有注册用户或所有预约邮箱 |

“申请提交率”如展示，须定义相同餐厅、时期和来源覆盖的口径；首版不把预约申请数/PV当成严谨的人级转化率，电话录入也不能算网页转化。访问未授权、机器人过滤和跨日申请都会影响数据。

## 13. 不存什么、存在哪里

### 13.1 数据库与外部存储分工

- 数据库：身份映射、归属、菜单结构、确认事实、固定快照、版本引用、预订、订阅、任务与指标。
- 对象存储：原始PDF、图片、生成HTML、必要的构建产物；使用storage_key与校验摘要关联。
- 密钥管理：数据库密码、模型API密钥、邮件密钥、加密密钥；绝不放在商家表、HTML或普通日志里。
- 可短期重建数据：预览签名URL、任务租约、限流状态。它们不作为长期业务事实。

### 13.2 不收集/不持久化

顾客支付卡资料、政府证件、生日、精确定位、跨店行为画像、隐藏模型推理、无限期完整IP、管理令牌明文、未授权通讯录；首版不需要这些。顾客备注可能含敏感信息，限制提示、权限和保留，不能把备注发给建站模型。

### 13.3 保留与删除建议（待首发国家及政策确认）

| 数据 | 建议基线 | 清理要求 |
| --- | --- | --- |
| 预订联系信息 | max(requested_start_at、最后处理/取消时间)后90天为初始产品建议，不是法律结论；未处理pending先按明确超时政策关闭 | 没有实际到店记录，不用“服务完成”虚构清理起点；到期置空个人字段，保留必要非个人计数 |
| 原始访问事件 | 30天 | 清理标识和事件；只保留不可关联个人的日汇总 |
| Agent对话与失败中间稿 | 完成后90天 | 保留经确认资料，删多余原始对话和临时内容 |
| 认证/业务令牌 | 按用途短期到期，退订令牌另按邮件有效期 | 改密/确认一次性令牌使用后清理；预订管理到期后清理；有效退订链接不按一次性确认规则误删 |
| 邮件正文/payload | 发出或失效后30天以内 | 短期动作密文尽快删除；保留必要状态而非永久全文 |
| 审计 | 180天的起始建议 | 不含多余PII；监管/合同要求另外核定 |
| 营销同意/抑制 | 按有效授权、争议与发送政策设定 | 保留最小撤回/抑制证据，不能删除后重新导入发送 |
| 发布版本和素材 | 当前版本＋有限可回滚版本 | 先检查引用；删HTML版本不删预订事实 |

用户删除：删除身份凭据/会话/令牌，users保留不含邮箱/姓名的deleted身份墓碑以维持必填历史外键；活跃身份必须有邮箱，deleted身份邮箱置空，并仅对非空登录键做唯一约束。customer_user_id、可选操作者ID可置空，不能让用户删除级联摧毁菜单、网站或预约。商家owner删除前必须先移交或关闭餐厅。

预约匿名化置空guest_name、guest_email、guest_email_normalized、guest_phone、guest_note、internal_note、customer_user_id，写anonymized_at并撤销管理令牌；有效业务记录字段必填，anonymized_at非空的历史行允许这些字段为空。事件JSON、发送payload和引用快照也同步清理相关个人信息，预约日期/人数/状态的必要计数按明确目的保留。订阅删除须保留受保护的最小撤回/抑制证据，不能清理后自动恢复发送。有限期同意证据不能无限保留。匿名化不能被全量同步/模型重新生成逆向恢复。

商家关闭：停止公开网站与新申请、处理尚未完成预订、再执行分层数据清理。备份有独立保留期和恢复后的删除重放机制；不能承诺删除即时消除所有历史备份。

## 14. 首版验收与待确认项

### 14.1 数据验收

- 商家注册、餐厅创建、菜单确认、生成、发布均有真实可恢复记录。
- 跨店读取和引用失败；游客链接不能查看别人预订。
- 重复提交产生一笔申请；并发商家处理只接受一个revision，通知跟随最终事件。
- 生成、发布重试不覆盖旧正式站，不修改已有预订和邮件订阅。
- 预览不进入reservations、email_outbox和正式visit_events指标。
- 客户端伪造status、restaurant_id、user_id无法越权。
- 用户注册不自动变成营销subscribed，退订后旧确认链接不能恢复授权。
- 邮件失败可查；外部供应商超时不能盲目重复发送。
- 服务重启及备份恢复后，关联、索引、网站引用、预订与同意历史可以核对。

### 14.2 尚需确认的产品选择

1. 无容量管理时，是否采用人工确认申请？本稿按此设计。
2. 保留此前顾客可选注册需求；仅账号体验是否跨店统一、游客记录如何验证认领需确认，不擅自将注册移出首版。
3. 邮件仅做事务通知＋订阅收集，还是首版开放营销群发？本稿不默认加群发活动表。
4. 游客是否先验证邮箱？本稿预留验证字段，但不把无注册等同无验证。
5. 自定义域名、具体取消/改约规则和保留期限，后续确认后冻结；未确认不影响已确定核心字段。

## 15. 最终建议

把“商家能填的固定内容”“AI提取草稿”“已发布网页快照”“真实预订和订阅数据”分开保存。首版固定数据字段和业务契约，视觉设计可变化，后端集中负责权限和业务；让模型生成页面，不让模型定义表结构或决定预订状态。

最重要的长期字段是restaurant_id、稳定业务ID、内容revision、网站版本、预订状态/事件、营销同意历史及幂等键。它们让第一版即便功能少，也具备隔离、可靠更新、失败重试和后续扩展的基础。
